# Stars: star rating, mood, grudges and the trailer component

How a star's rating is built from its components and what feeds them, star mood, the grudge system, and the `CStar` / `CTrailerData` decoding. Companion to `MOVIE_SUCCESS.md`, `TRAITS_AND_EXPERIENCE.md` and `CHARACTERS.md` (people in a save). Labels: **[code]**, **[config]**, **[measured]**. Section labels (3k, 3aa, ...) are stable identifiers that other documents and code comments cite; they are not a reading order.

## 3y. Repair work and the star grudge system (decoded from `DesireTaskRepairman_*` and `global.ini`) **[code + config]**
A repair job is a `task_repairman` desire (`DesireTaskRepairman_Constructor`, 0x840FD0) given to a staff member or star by the building's `heal` task (`STUDIO.md` 3q). While it runs, `DesireTaskRepairman_UpdateProgress` feeds the asset activity's progress to the animation channel `ai_progress`; on completion the worker gains Lot experience (`LOT_PERHAMMERREPAIR` 0.0003 per hammer blow in `experience.ini`; each blow does `repairworkperhammermin/max` = 0.5..1.5 work units, and a building's `repairwork` (5..50 units, 3r) is the total needed). **If the worker is a star, giving them repair work creates a grudge:** the constructor calls `CGrudges_AddOrRefreshGrudge` with `[star] dislikestaffjob = -0.4` and recovery `forgivestaffjob = 0.0002` (key `grudge_staff_job`) - so stars should never be sent to repair or build. Other grudge parameters in `global.ini [star]` (dislike / recovery per tick): pay cut -0.5 / 0.0001, worse trailer -0.3 / 0.0001, paparazzi photo -0.5 / 0.0001, actor-director swap -0.3 / 0.0001, being fired -0.1 / 0.0001, photo of sex -0.3, photo at detox -0.1, unfulfilled desires -0.5 (staff) / 0.0001, being grabbed (dragged) 0.1 (staff) or 0.75 x ego (stars); positive feelings: pay rise +0.5 (forgetting -0.0001), release a movie +0.3 (-0.00025), hire 0.0 (-0.000417), award +0.1 (-0.000008), feeding an addiction +0.3 (-0.00025), auction win +0.25 / lose -0.25, being given an assistant +0.15. Practical rule: the only large, fast-decaying positives are releasing movies, pay rises and addiction feeding; the large negatives are pay cuts, paparazzi photos, repair jobs and worse trailers, and each recovers at about 0.0001-0.0002 per tick (so recovering 0.4 takes thousands of ticks).

## 3z. What star mood does (decoded) **[code + `mood.ini` + `releasing_movies.ini`]**
**Effect on films:** `CStar_GetMoodPerformanceFactor` (0x5D79A0), called by `QualityCalc_ActorPerformance`, turns the star's mood `m` (0..1) into an acting multiplier between `star_mood_min` 0.8 and `star_mood_max` 1.2 (`releasing_movies.ini [min_max]`): `factor = 0.8 + 0.4*f`, where `f` is a stepped curve in three bands set by the cast effect's **lower and upper mood thresholds** (`CProjectCastEffect_GetEffective{Lower,Upper}MoodThreshold`; the Easy To Please award bonus caps them at **lower 0.15 and upper 0.75**, `lower_mood_val`/`upper_mood_val`): below the lower threshold `f` rises from 0 over the low band (factor 0.8 up to about 0.9), between the thresholds it is a flat middle value (`f` = 0.5, factor 1.0), and above the upper threshold it climbs through the top band toward 1.0 (factor about 1.1 up to 1.2). The band widths come from `star_mood_step` (0.25 in the ini) held in a runtime global (`0x104D7CC`) that I have not yet read from a running game, so the exact band edges (0.8-0.9 / 1.0 / 1.1-1.2) are the expected values, not measured. In plain terms: **a star in a good mood (above the upper threshold) acts up to 20% better, an unhappy star (below the lower threshold) up to 20% worse, anything in between is neutral; Easy To Please lowers the bar so that the penalty zone (mood under 0.15) is smaller and a mood above 0.75 already earns the bonus.**
**Correction from the decompile of `CStar_GetMoodPerformanceFactor` (`0x5D79A0`; implemented in `web/src/sim/movie/ActorPerformance.ts`):** the three bands are linear inside and do not join up, and the middle is not flat. With `star_mood_step` s = 0.25 and outer width w = (1 - 2s)/3 = 1/6: mood below the lower threshold L gives `f = mood / L * w`; between L and U `f = (s + w) + (1 - 2(s + w)) * (mood - L)/(U - L)` (5/12 .. 7/12); at or above U `f = (1 - w) + w * (mood - U)/(1 - U)` (5/6 .. 1). The factor is `0.8 + 0.4 f`, so about 0.8-0.87, 0.97-1.03 and 1.13-1.2. Any mood or threshold outside 0..1 gives 0.8. Still not measured in a running game.
**What moves mood** (per-tick stress / boredom deltas, `Data/mood.ini`): working on a movie +0.00006 / -0.0004 (so a working star gets more stressed but less bored); rehearsing +0.00006 / -0.0002; stunt training +0.00006 / -0.0002; waiting on a movie +0.00003 / 0; doing PR +0.00002 / -0.0004; make-over +0.00002 / 0; health clinic +0.0002 / -0.0002; **staff jobs +0.0002 / +0.0002 (the worst activity: both go up)**; restaurant -0.0003 / -0.0003; snack van -0.00015 / -0.00015; drinking -0.0003 / -0.0003; eating or drinking on the spot -0.0002 / -0.0002; idling -0.000008 / +0.00004; trailer (alone or together) -0.00008 / 0; detox 0 / -0.0002; hospital +0.00004 / +0.00004. Health also feeds mood (`MOODHEALTHINJURY` -0.2, range -0.4..0), and `MAXIMUMBOREDOMONPROJECT` caps boredom from one project at 0.19. Practical rule: stress builds slowly while stars work and falls fastest with restaurants and drinking (-0.0003) and in the trailer (-0.00008); boredom is relieved by working, so a star who is kept busy is rarely bored, and a star left idle slowly gets bored (+0.00004). The mood HUD behaviour of `CStar_ChooseWalkAnimationByMood` (0x58F440) switches the star to complaining/idle animations when the mood value crosses two thresholds (`0xD26EAC`, `0xD26EB0`).

## 3aa. Star rating components (partly decoded while naming CStar functions) **[code + `global.ini`]**
`CStar_ComputeStarRating` combines components with the weights in `global.ini` (`starratingweightmovies` 0.174, `salary` 0.139, `performance` 0.139, `image` 0.104, `entourage` 0.104, `trailer` 0.104, `pressbar` 0.102, `relationships` 0.07, `awards` 0.07). Decoded so far (each result is cached on the star and clamped to 0..1): **salary** `CStar_ComputeSalaryComponent` (0x587D40; for your own stars it maps the salary from the salary-costs object through a curve, for other studios' stars a cached value at `+0xD28`; the result is stored at `+0xD20`); **relationships** `CStar_ComputeRelationshipsComponent` (0x58F9F0; for your own stars it sums, over the other stars of your studio, a term from the pairwise relationship value `(r - 0.5)*2` weighted by the other star's own level, stored at `+0xD1C`); **body appearance** `CStar_ComputeBodyAppearance` (0x587100; `((1 - (weight - 60) * 0.025) + look value at +0xBC8) * 0.5`, one input of the image component below). The performance, trailer, entourage, movies and press components are not yet identified.

## 3ab. Star rating: the full formula (`CStar_ComputeStarRating`, 0x591720) **[code + config; two components still open]**
`rating = clamp01( S + base )`, where `base = star+0xCCC` (an unweighted term) and `S` accumulates `clamp01(weight_i * component_i)` for nine components with a clamp to 0..1 after each addition. Weights are read from `global.ini` into `StarRatingWeight_*` (renamed): **movies 0.174, salary 0.139, performance 0.139, image 0.104, trailer 0.104, entourage 0.104, press bar 0.102, relationships 0.07, awards 0.07** (they add to 1.006). Components (all clamped 0..1 and cached on the star; for stars of other studios the game uses cached values instead of recomputing):
- **salary** (`CStar_ComputeSalaryComponent`): mapped from the star's current salary through a curve (not decoded further).
- **relationships** (`CStar_ComputeRelationshipsComponent`): over the other stars of your studio, `sum((r-0.5)*2 * (otherLevel*0.5+0.5) * k)`, with `r` the pairwise relationship value.
- **image** (`CStar_ComputeImageComponent`, 0x5909C0): built from the costume value (`CStar_ComputeCostumeImageValue`, 0x58FB60: how fresh the current costume is against its wear dates, then adjusted by cosmetics: `femalebeard` -0.65, `maleeyeshadow` -0.1, `malelipstick` -0.1, `malenailvarnish` -0.05 from `global.ini [star]`), the body appearance (`weight`/look) scaled `* 0.6 + 0.4`, and a second appearance term from virtual slot 0x238; the terms are then combined by a small formula over the minimum of the two plus a function of each (not decoded in detail).
- **trailer** (`CStar_ComputeTrailerComponent`): for your own stars the value returned by virtual slot 0x268 (the star's trailer quality); otherwise the cached value (`+0xD30`).
- **entourage** (`CStar_ComputeEntourageComponent`): number of entourage members x **1/6** (so six members give the full value).
- **awards** (`CStar_GetAwardsRatingComponent`): number of awards the star has won x **0.526** (two awards cap it), cached with the date it was computed.
- **movies** (`CStar_GetMoviesComponent`, virtual slot 0x240): a decaying value (`DecayValue` at `+0xBD0`), see below.
- **performance**: a decaying value kept on the star (`DecayValue` at `+0xBDC`, read by `DecayValue_GetClamped01`), see below.
- **press bar** (`PressBar_GetClampedValue`): the value of the star's press bar object (`+0x344`), the bar the publicity room fills.
Practical reading: about 1/6 of the weight is directly buyable (salary 0.139), 1/10 each is entourage (hire six staff), image (fresh costumes, no cosmetic penalties), trailer and press bar (publicity sessions), awards cap quickly (two awards give the full 0.07), and the two biggest terms, movies (0.174) and performance (0.139), come from the star's film record.

## 3ac. What feeds the two biggest star-rating components (movies 0.174, performance 0.139) **[code + config]**
After a film is released the game updates every member of its cast and its director: `CProject_ApplyReleaseToCastRatings` (0x5AE9C0, for the player's films) and `AIMovie_ApplyReleaseToCastRatings` (0x5A3EA0, for AI films) call two virtual functions of `CStar`: **`CStar_AddMovieRating(S)`** with the film's success `S` (`CProjectSuccess_GetClampedSuccess`, the validated success value of section 2, clamped 0..1) and **`CStar_AddPerformanceRating(p)`** with the star's mean performance score over the film's shots (`CProject_GetMeanPerformanceForPerson`). Each call adds `clamp01(ratingsmultiplier * value)` = `0.4 * value` to the star's decaying value (`+0xBD0` for movies, `+0xBDC` for performance), and each value then decays exponentially with the half-life `ratingshalflife` = 10 (game years, the same `DecayValue` machinery as boredom). The performance call also gives the star a grudge update `likereleasemovie` +0.3 (recovering at `forgivereleasemovie`, see 3y), so releasing a movie with a star in it improves that star's feelings as well as their rating. Examples: a cast member in a film with S = 0.8 gains 0.32 on the movies value immediately (before the 0.174 weight, i.e. +0.056 of rating); two such films within a few years push the value near 0.6, three near 0.9, and the value falls to half after ten years without new films. A flop (S = 0.3) adds only 0.12. So the way to raise a star's rating is a steady run of high-S films with them in the cast, and keeping them acting well (shot performance) feeds the second term. `CStar_AddGenreBoredom` (virtual slot 0x24C) is the third update on release: it adds `genreboredomboost` 0.1 to that star's boredom for the film's genre (`MOVIE_SUCCESS.md` 3c).

## 3ad. Staff job numbers (`CStaff+0x814`, `CStar_SetJob`; established earlier in the project, copied here so it lives in the repo) **[code + `tasks.ini`]**

(The camera/sound/clapper/assistant sub-roles are shown to the player as one "film crew" job; the game picks the sub-role per shoot.) ## 3af. More CStar decoding
- **Drunk level** is a float at CStar+0xb9c (`CStar_GetDrunkLevel`). `CStar_IsDrunk` = level > globals 0xD26EAC (also the `ai_drunk_thresh` channel value); 0xD26EB0 is the "very drunk" threshold (`ai_vdrunk_thresh`, drunk-advice thought). `CStar_ChooseWalkAnimationByMood` plays animation 0x2b/0x2a (drunk, by gender) or 0x2c (very drunk) above those thresholds.
- **Weight** is a float at +0xb3c (`CStar_GetWeight`). `CStar_ComputeBodyAppearance` = clamp01(((1 - (weight - 0xD26EB4) * 0xD24914) + (+0xbc8)) * 0xD26EAC).
- **Image component** (`CStar_ComputeImageComponent`, cached at +0xd18): three values (costume image value, body appearance scaled, virtual 0x238 value) are combined by summing a transform of each plus the smallest; result clamped 0-1. `CStar_ComputeCostumeImageValue` mixes a time-based fade (+0xd0..+0xd8 times), the star's age against the costume's age band (+0xdc/+0xe0), body appearance, and `CStar_GetCostumeFlagImageBonus` bonuses for costume flags 3, 4, 5 (gender-gated) and 0xc.
- **Other components cache the non-player value**: for stars not owned by the player studio, salary (+0xd20), relationships (+0xd1c), trailer (+0xd24) and entourage (+0xd14) use stored fallback values at +0xd28/+0xd2c/+0xd30/+0xd34; only player stars are recomputed. Entourage = member count (list at +0xa50) * 0xD17190 (1/6 per member, as already noted). Press bar value is +0xd10's clamped value or the fallback +0xd38.
- **Relationships component** sums, over other player-studio stars, `(rel - 0.5)*2` weighted by `(other.rating(+0xcd0)*0.5+0.5)` times a global (0xD2794C).
- `CStar_NormalizeSalaryToBudget` divides a salary by a per-studio budget scale (0xD195BC) and clamps 0-1: this is the salary term's shape.
- `CStar_GetPlayerStarsRmsRating` returns the RMS of +0xd54 (final rating) over stars of the player studio.

## 3as. CTrailerData and remaining CStar names
**CTrailerData** (0x6a8 bytes) is the stored trailer of a project (created lazily at CProject+0x16c, `0x5B25F0`). It is not the star-rating trailer term itself (that is `CStar_ComputeTrailerComponent`, which reads a value from the star through virtual slot 0x268). The class holds the trailer's title (+0x60/+0x80), author/path strings, per-shot data (record array at +0x200), and a 0x428-word header record. `CTrailerData_ParseFromBuffer` (0x7590F0) fills it from a serialized buffer (header record copied with `CTrailerRecord_Copy`, strings, dates, then the shot records), `CTrailerData_LoadFromPath` reads such a file (movies are stored under `<Documents>\The Movies\Movies\`, `Trailer_GetMoviesFolder`), `CTrailerData_Load` builds the path, loads and runs the same parser, and `CTrailerData_SaveLoad` embeds the blob in the save game (length + bytes; load constructs a `CTrailerData` and parses it). Files are integrity-protected: `Trailer_ComputeChecksum` hashes the payload (an MD5-style context) and appends a numeric checksum computed over every 11th/17th byte; `Trailer_FillPaddingAndChecksum` fills 0x400 bytes of random padding and the hash. `TrailerFlags_Build` emits three boolean flags (`FUN_00541F60(0..2)`).
**CStar**: the remaining small CStar entries were named: `CStar_GetAge` (time from the birth-like field +0x860 to the death-like field +0x864, or to now; `CStar_GetAdjustedAge` adds the offset +0xa44), `CStar_PlayBoredWalk / CStar_PlayHappyWalk`, `CStar_GetMoodFlagA/B`, `CStar_RecordTimeForKey` with its `StarTimeMap_*` helpers (a string-keyed map at +0xd5c of times), `CStar_UpdateLazyHelper`, `CStar_PostMoveUpdate`.

## 3at. The star's trailer quality (feeds the trailer component of the star rating)
Chain: `CStar_ComputeTrailerComponent` (section 3ab) for a player star calls virtual slot 0x268 = `CStar_GetTrailerQuality` (0x5876E0), which takes the star's trailer facility (virtual slot 0x270, a 3-instruction getter returning the `CFacilityTrailer*` stored at CStar+0xAD8; it is not defined as a function in Ghidra) and calls the facility's virtual slot 0x1CC = `CFacilityTrailer_ComputeQuality` (0x84CD90). The result is clamped to 0-1 and is the trailer term (weight 0.104 in the star rating).

**Trailer quality** (`CFacilityTrailer`, subclass of CFacility / TMFixedAssetLarge):
`T = clamp01( 0.2 * A + 0.3 * B + 0.5 * C )`
- A = (n0 + n1 + n2 + n3) * 0.25 / 16 = (n0+n1+n2+n3) / 64, with four integer counts at +0x55C, +0x560, +0x564, +0x568 (up to 16 each; presumably the number of upgrades / items in four categories).
- B = `CFacilityTrailer_ComputeItemsScore` = clamp01( 1.0 * sum of virtual-slot-0x160 values of the objects in the list at +0x170 ) (the trailer's furnishing items, constants at 0xE5D0B4 = 1.0).
- C = 0 if the trailer is in disrepair (`CAsset_IsInDisrepair`), else (condition * 0.5 + 0.5) * (value at +0x554), where condition is the facility's virtual-0xB8 float (state of repair, `STUDIO.md` 3q) and +0x554 is a per-trailer level float from its definition.
Constants: 0xD1A794 = 0.25, 0xE5D098 = 16, 0xE5D0A0/A4/A8 = 0.2 / 0.3 / 0.5.
Consequence: a neglected trailer (disrepair) loses the largest term (C, half the score), so repairs matter for star happiness through this term. Items behind B and +0x554 are decoded in 3au; still open: the writers of the four counts; the tracker's STAR_COMPONENTS rows can be checked against T once a game run is available.

## 3au. Trailer term B decoded (possessed assets, ornament impact) and the +0x554 field
**What the list at +0x170 is.** `CAsset_Constructor` (0x534F30) initialises +0x168/+0x16C/+0x17C as an `InList<TMFixedAsset>` (the saved variable at +0x170 is mislabelled `PFloorPlan` in the SLVAR macro). Each asset's owner pointer is `PPossessor` (+0x128), so the list is "assets possessed by this asset": for a trailer, the ornaments/decoration placed in it. `CFacilityTrailer_ComputeItemsScore` calls virtual slot 0x160 on each (node pointer at +8).

**Item value (virtual 0x160).**
- Default (CFacility and most TMFixedAsset subclasses, 0x528030) forwards to slot 0x15C: `CFacility_GetAppealValue` (0x5291C0) = `1.0 * attractiveness(+0x2bc) + 0.5 * condition - 0.5` (condition = virtual 0xB8, state of repair).
- `COrnament` (and `CSponsoredBillboard`) override both slots:
  - slot 0x160 (`COrnament_GetImpact`, 0x48A770) = `slot15C / k`
  - slot 0x15C (0x48C660, not a Ghidra function yet) = `(attractiveness(+0x2bc) / s(+0x430)) * D`, where `D = 1 - 0.5 * (atan(n/2 - k)/pi + 0.5)`
  - `k` = definition field `impacthalfcount` at +0x47c (default 9.0, `COrnament_LoadDefinition` 0x48B190); `s` = +0x430 (initialised to 1.0 in the constructor; writer not found yet); `n` = number of COrnament instances of the same type key (+0x35c) in the whole world, from `COrnament_GetCountOfType` (0x48C5D0; the per-key count map at 0x104A5F8 is rebuilt lazily when the flag at 0xE50978 is set by a constructor).
  - `D` falls smoothly from 1.0 to 0.5 as the number of identical ornaments grows past about `2k`.
- Constants verified from the exe: 2.0 (0xE5098C), 0.5 (0xE50984), 1/pi (0xD1CAE0), 0.5 (0xD1694C).

Per-item value with attractiveness a and default k = 9, s = 1 (D shown, then a-multiplier): n=1: 0.981, 0.109a; n=9: 0.965, 0.107a; n=18: 0.75, 0.083a; n=36: 0.518, 0.058a; n=100: 0.504, 0.056a. So B = clamp01(sum): about nine distinct, attractive ornaments of attractiveness 1 saturate the term, and filling the trailer with copies of one ornament yields less than half value per copy once there are ~36+ in the world.

**+0x554 / +0x558** are set by `CFacilityTrailer_LoadDefinition` (0x84C640, slot 0x1A4) from the definition node: `quality` (clamped 0..1) -> +0x554, `territory` -> +0x558. So term C = (condition*0.5+0.5) * definition quality: the trailer's own tier. The four ints at +0x55C..+0x568 are zero-initialised in `CFacilityTrailer_Constructor` (0x84C9A0); the code that increments them is not found yet (A = sum/64).

Open: the +0x430 writer (assumed 1.0), whether other asset types (non-ornament) can be possessed by a trailer, and the writers of the four counts. Check with the tracker once a run has STAR_COMPONENTS and a trailer's ornament list.
