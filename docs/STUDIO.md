# The studio: buildings, facilities, decoration and the studio rating

Building condition and repair, facility parameters, fixed assets and activities, room slots, the lot-wide metrics and the studio star rating. Companion to `MOVIE_SUCCESS.md` and `SAVE_FORMAT.md` (placement, terrain). Labels: **[code]**, **[config]**. Section labels (3k, 3aa, ...) are stable identifiers that other documents and code comments cite; they are not a reading order.

## 3q. Building condition and disrepair (decoded) **[code]**
Every building/set asset (`CAsset`, base class; facilities derive from it) has a condition float at `+0x2C4` (starts at 1.0 in `CAsset_Constructor`), a lifespan duration at `+0x2C8` and a decay start date at `+0x2CC`. `CAsset_UpdateConditionAndDisrepair` (0x5343D0, runs each update): if the tutorial/cheat object (`DAT_0104A974+0x68`) is set, condition is pinned to 1.0 and disrepair is cleared. Otherwise, once the decay date has passed, condition falls by `(1/dayLength)/lifespan` per update, i.e. **linearly from 1.0 to 0 over its lifespan**; when it reaches 1.0 again the `task_repairman` job is cleared. **Disrepair has hysteresis:** the flag at `+0x2E4` (`CFacility_IsInDisrepair`) is set when condition `<= 0.05`, records the date at `+0x2E8`, posts `TANNOY_BUILDINGS_IN_DISREPAIR` and starts spark effects; it is cleared only when condition `>= 0.95`. Separately `CFacility_UpdateVisualsAndRunningCosts` posts `TANNOY_DISREPAIR_WARNING_FACILITY` once when a facility's condition drops to `<= 0.10` (flag `+0x2E5`, re-armed above 0.10). `CAsset_ClearDisrepairState` (0x527FD0) resets the timer, the disrepair flag and the warning flag. A facility that is in disrepair counts as unavailable (`0x4CA9F0` returns "blocked" if `IsInDisrepair` or the flag at `+0x55C`), and the marketing facility keeps a global working-count (`DAT_0104ED68`) that is decremented when a facility that is not in disrepair is destroyed. Practical effect: a building is fully usable until condition 0.05 and unusable from then until a repairman (task `task_repairman`) restores it above 0.95, so repair crews must be sent well before a building reaches the low warning at 0.10. The asset state at `+0x2B8` is decoded by `CAsset_UpdateStateMachine` (0x5347F0): **0** idle; **1** placed, waiting for a builder (set by `CAsset_OnPlaced` when the building has construction work, `+0x2DC` > 0; at the ready time `+0x3B4` it moves to 2); **2** under construction (the `task_builder` job is active until the building work is done); **3** being demolished (`CAsset_BeginDemolish`, removes the asset when its timer expires); **4** placed with no construction work (instant build: when the timer expires it finishes and copies the work value); **5** operational (`CAsset_SetOperational`; the default in the constructor): in state 5 the builder task is switched off, the condition update of 3q runs, and if the building is in disrepair the `heal`/repair task is activated. So states 1-2 are the 'being built' stages that `buildingwork` in the facility ini controls, 3 is demolition and 5 is the normal working state.

## 3r. Facility parameters from `Data/facility/*.ini` **[config]**
Keys per building: `purchasecost`, `annualcost` (0 in every shipped file), `dailyrate` (0), `decaytime` (the asset lifespan of 3q, probably in years: condition falls from 1.0 to 0 over it, so a building is usable for about 95% of it), `repairwork` (work units the repairman needs), `ETA` (the year the building becomes available), `maxinstances` (-1 = unlimited), `capacity`, `researchable` (0 everywhere). So facilities have **no running cost in the data**; their only recurring cost is repair labour and replacement. Purchase cost / decaytime / ETA: bar 8000 / 2.6 / 1920; catering1 3000 / 2.4 / 1905; catering2 30000 / 1.8 / 1920; cosmetic surgery 60000 / 2.5 / 1900; crew 4000 / 2.7 / 1906; custom script 11111 / 1.95 / 1900; detox 22000 / 2.7 / 1900; fight room 9000 / 4.0 / 1970; full-body burn 6000 / 4.0 / 1970; spartan 3000 / 4.0 / 1970; hospital 25000 / 2.5 / 1900; post-production 39000 / 3.8 / 1900; pre-production 5000 / 2.4 / 1900; production 6000 / 2.6 / 1900; **publicity office 44444 / 2.5 / 1900 (unlocked by rank 4, not by date)**; research 24000 / 3.2 / 1900; script offices 1-4 star 6000 / 29000 / 33333 / 66666 with decay 2.6 / 2.3 / 2.7 / 3.0 (unlocked by ranks, ETA 1900); sell 3000 / 2.2 / 1906; stage 5000 / 2.0 / 1905; **stunt facility 5000 / 2.0 / 1969**; toilets 1-3 3000 / 12000 / 20000 with decay 0.9 / 1.2 / 3.0 (ETA 1905 / 1915 / 1915); wardrobe 7000 / 2.6 / 1900; trailers 1-5 7000 / 24000 / 45000 / 75000 / 77777 with decay 1.9 / 2.2 / 2.3 / 2.5 / 3.2 and ETA 1931 / 1949 / 1958 / 1967 / 1976. Shortest-lived buildings are toilet 1 (0.9 years) and toilet 2 (1.2 years), so they need the most repair visits and replacements; per year of life toilet 1 costs 3000/0.9 = 3.3k, toilet 3 costs 20000/3.0 = 6.7k (assuming decaytime is in years, which I have not verified).

## 3ae. TMFixedAsset (CAsset_*) and TMActivityManager decoding
**CAsset_LoadDefinition (0x52BF80)** reads a facility's definition node (CAsset+0x408 via `CAsset_GetDefinitionNode`) with these keys:
mesh (+0x37c), classiness (+0x2c0, clamped 0-1), initialrotation (+0x214, degrees to radians), fertility/blanket (+0x2a4), name (+0x31c), attractiveness (+0x2bc), ownable (flag 0x400 of +0x2e0), randomangle (flag 0x8), capacity (+0x318), maintenance block (decaytime, repairwork +0x2d0, buildingwork +0x2d4, rebuildingwork +0x2d8), camera/primary viewposition and viewfocus, blueprint block (path; path group_catering sets flag 0x2000, group_toilets 0x4000; availableindebt -> +0x3f1), finance block (annualcost, dailyrate, purchasecost -> finance object at +0x2a0, `CAsset_GetFinance`).
Earlier note "facility ini has no running costs" should be re-checked against this: the loader reads annualcost/dailyrate and passes them through `Money_DebugCheckRange`, so the values may simply be absent from the shipped data.

**Capacity totals**: `CAsset_Deactivate` subtracts capacity (+0x318) from `g_TotalToiletCapacity` (0xF89040, flag 0x4000) or `g_TotalCateringCapacity` (0xF89044, flag 0x2000). `CAsset_PostPlacementTip` posts `PIP_PLACING_CATERING_UP/DOWN` and `PIP_PLACING_TOILETS_UP/DOWN` advice tips to the player studio when the totals are below 1.0.

**Repair** (`CAsset_ApplyRepairWork` 0x52BD10): a character with the "Lot" trait adds to condition (clamped 0-1); when condition reaches exactly 1.0 the player studio gets `PIP_BUILDING_REPAIRED_INCREASED` and `CAsset_DismissRepairmen` stops all characters running `task_repairman` for this asset. `CAsset_CreateMeshTaskNodes` turns mesh nodes named build_/repair_/moveasset/deleteasset/leansmoke into task nodes (repair -> task_repairman, build -> task_builder, leansmoke -> leanspot).

**CAsset_UpdateStateVisuals (0x52F790)** switches on the asset state at +0x2b8 (0 idle, 1 waiting for builder, 2 under construction, 3 demolishing, 4 instant placement, 5 operational, same enum as 3q) and fades/scales the models.

**TMActivityManager** is not a scheduler: it drives the shared "puppet" scene of characters doing one activity together (default scene `ai_puppet_wait.flm`). Participants are a list at +0x1b4, scene at +0x214; channels read: ai_action, ai_satisfyloop, ai_drunk, ai_ai*. It prunes finished participants (`RemoveOneFinishedParticipant`), stale entries every 500 ms, and forwards drunk level from the character.

**Save-game variables** (`CAsset_RegisterSaveVariables` 0x52A850, via the SLVAR macro in TMFixedAsset.cpp lines 0x92-0x9d): SourcePath, PFixedAssetCosts (+0x214 pointer), Knackered (+0x26c, 1 byte), NearlyKnackered (+0x26d), StateOfRepair (+0x24c, the condition value), (int&)State (+0x240, 4 bytes), BuildWorkDone (+0x340), BuildWorkNeeded (+0x264), DecayBegin (+0x254), PPossessor (+0x128, owner pointer), PFloorPlan (+0x170), IsAlwaysAvailable (+0x379). "Knackered"/"NearlyKnackered" are the disrepair (<=0.05) and warning (<=0.10) flags of section 3q. Offsets are those passed to the serializer; the live state byte used by the state machine is at +0x2b8.

Other: `CAsset_SpawnOrnaments` (0x52B430) reads the definition's `extra_info/ornaments` list (type, offset, angle or RANDOM) and spawns `ornament/<type>` objects; `CAsset_Activate`/`CAsset_Deactivate` add/subtract capacity to the toilet/catering totals; `CAsset_OnPlaced` ends placement mode, posts the placement tip and the `PLACE_<name>` event.

**TMActivityManager channels** (`TMActivityManager_SetupCharacterChannels` 0x405040): per character it seeds the puppet scene channels ai_male (1.0 unless the character has an owner), ai_star (1 for a star), ai_drunk (+ ai_drunk_thresh / ai_vdrunk_thresh globals 0xD26EAC/0xD26EB0), ai_stressed, ai_happiness, ai_celebrity (= star rating, `STARS.md` 3aa), ai_boredom, ai_trailerhappiness. The animation scene (.flm) reads these to choose behaviour, so mood and star rating directly drive puppet animation. Lifecycle: LoadPuppetScene -> AddParticipant -> Start -> UpdatePuppet each frame -> OnParticipantFinished/ReleaseParticipant -> Shutdown (cancels every participant's action and drops the refcount).

## 3am. TMRoomSlotManager
A room has a slot manager (TMRoom +0x228, created lazily by `TMRoom_GetOccupantManager`, 0x5c bytes). It owns an array of slot pointers (+0x20..+0x24) and a table of slot positions (+0x30, 16 bytes per slot: x, y, z, angle; `SlotManager_GetSlotPosition` / `GetSlotAngle`). The manager's constructor takes the room and an `ai_<room>.flm` scene name (+0x3c). Each slot (`RoomSlot`, 0x34 bytes) links a character (+0x14), a room-activity target (+0x2c) and a slot index (+0x30). `SlotManager_AssignSlot(character)` takes the first free slot, builds a `RoomSlot`, and (in room mode, flag +0x1c9 of the room) starts a `CActivity` for the character (`SlotManager_StartActivityForSlot`: sets the activity's desire name from the room, adds the resident desire and the action to the character, and moves the character to the slot position when it has one). `SlotManager_EnsureSlotForCharacter` reuses an existing slot, `SlotManager_ReleaseSlotForCharacter` frees it and returns the index, `SlotManager_SetSlotSceneChannel` writes a named animation-scene channel for the slot's room scene, `SlotManager_SetSlotCount` resizes the array (and clears it).

## 3av. TMInWorld, TMFloorPlan, COrnament and the studio decoration ratio
**TMInWorld** (`TMInWorld.cpp`, base of placed/world objects; ~20 names `TMInWorld_*`). Save variables (`TMInWorld_RegisterSaveVariables` 0x539430, offsets are sub-object-relative, sub-object at +0x78): `Position` (12 bytes, real +0x100), `MyAngle` (float, real +0xC4), `GUID` (real +0x13C). `TMInWorld_AllocGuid` / the constructor take GUIDs from a global counter (0xE52870). The object also keeps a mesh/scene object pointer at +0x11C, a cached GUI object (`TMInWorld_GetCachedGuiObject`, +0x144), and click handling on key 0x73 (`TMInWorld_UpdateClick`, press under 0x15E ms = click, 0xFA ms for the input-state variant). `TMInWorld_GetWorldPosition` returns the mesh position (+offset if flag +0xFC) or the stored position. `TMInWorld_RayToPlane` projects a screen point onto a horizontal plane with the global camera (0x105C2E8). `TMInWorld_PostUIEvent("UI_ROOM_HIGHLIGHT" ...)` posts named UI events.

**TMFloorPlan** (a CAsset-owned set of rooms; `TMFloorPlan_*`): rooms vector at +0x228, 0x18-byte stride with the room pointer at +0x14 (count at +0x234 via `RoomVector_Size`), owner asset at +0x24C, current room at +0x210, "hover/select" flag +0x255. `TMFloorPlan_CountOccupantsByKind` sums `TMRoom_CountOccupantsByKind` over all rooms into three counters; `_GetRoomAtPoint`, `_GetRoom(index)`, `_FindRoomByShortName` (compares the part of the room's display name after the second `_`), `_CanDropHere` / `_DropObject` (drop a TMMobile or CProjectObject into the current room if `TMRoom_CanAcceptOccupant` and the room's own accept check pass), `_UpdateRoomHighlights`, `_PulseHighlightedRooms`, `_Tick` (posts `UI_ROOM_HIGHLIGHT`), `_ReleaseRooms`.

**COrnament** (`COrnament_*`, ~20 names): see 3au for the impact formula. Lifecycle: `COrnament_Activate` adds the ornament's attractiveness (virtual 0x15C) to the global `g_TotalOrnamentAttractiveness` (0xF89048) once (flag +0x478); `COrnament_Deactivate` and the destructor subtract it again. `COrnament_ResetState` sets `g_OrnamentCountsDirty` (0xE50978), which makes `COrnament_GetCountOfType` rebuild the per-type counts the next time they are asked for. `COrnament_CanBuyHere` checks that the cursor is inside the lot, that the finance object allows purchase and that the player can afford it (`Money_IsAtLeast`, money stored as 64-bit with 2^-23 scale). `COrnamentCopyManager_*` handles copy/paste of an ornament as a ghost with the HUD highlight `HUD_ORNAMENT_HIGHLIGHT`.

**Studio decoration ratio.** `Studio_GetDecorationRatio` (0x466180) = clamp01( `g_TotalOrnamentAttractiveness` / (3 * max(N, 2) + 2 * max(M, 4)) ) where N = length of the list at studio+0x94 (`FUN_0050ab40`) and M = studio virtual 0x8C (returns an int, likely staff/people count). The analogous `Studio_GetCateringSurplusRatio` (0x465F40) = clamp01( (g_TotalCateringCapacity - need) / need ), need = 0.5 * (0.1 N' + 0.05 M'), and `Studio_GetToiletSurplusRatio` (0x466060) uses g_TotalToiletCapacity and need = 0.5 * (0.25 N' + 0.1 M'), with N' = max(N,2), M' = max(M,4).

`CStudioPlayer_UpdateAppearance` (0x518570, formerly `Studio_UpdateEnvironmentScore`; runs from the player-studio tick 0x519450 whenever a timer at +0xA9*4 elapses) writes the studio's **appearance** at studio+0x12C (byte offset; an earlier note said +0x4B0, which was a misread of `param_1 + 300`) = clamp01 of:
- clamp01(0.30 * x1), x1 = `FUN_00452af0(DAT_00f88720)` (not decoded)
- + clamp01(0.25 * lot virtual 0x188) (not decoded)
- - 0.25 * (1 - lot virtual 0xB8) (the lot's condition / state of repair)
- + clamp01(0.05 * catering surplus ratio)
- + clamp01(0.05 * toilet surplus ratio)
- + clamp01(0.05 * decoration ratio)
- - 0.05 * (1 - cleanliness(0x466290))

Constants verified from the exe (0xE52190..0xE521A8, 0xE50418..0xE50434). The consumers of the appearance are decoded in 3aw; the meaning of x1 / lot virtual 0x188 is still open.

## 3aw. Studio appearance and the studio star rating (CStudio_ComputeStarRating)
**Readers of the appearance (studio +0x12C).** CStudio/CStudioAI/CStudioPlayer all share virtual slot 0x80 = getter for +0x12C (0x50AB30, not a Ghidra function). It is read by (a) `CStudio_ComputeStarRating` (0x50AB70) and (b) the advice-tip classes `PIP_PLACING_APPEARANCE_UP/DOWN` (getter 0x958A30 and compare 0x958A50, which also compare the lot's virtual 0x188). A second writer is the smoothing code at 0x513BF0 (adds/subtracts a clamped amount using studio +0x26C/+0x270/+0x274 and a 0.1 factor), so the appearance is moved gradually, not only set by `CStudioPlayer_UpdateAppearance`.

**The studio rating** (stored at studio +0x130, getter = virtual slot 0x84, 0x50AB60), recomputed every studio tick by `CStudio_ComputeStarRating` (0x50AB70, called from 0x50CC00). **[verified against the log: 27 studio rows (player and AI), within 1e-4 in 26 and 1e-3 in the other]** Each step is clamped to 0..1:
```
s = clamp01( 0.144 * appearance )                          // studio +0x12C, virtual slot 0x80
s = clamp01( s + 0.239 * DecayedReputation )               // CStudio_GetDecayedReputation 0x50A860
s = clamp01( s + 0.239 * money )                           // virtual 0x90, CStudio_GetMoneyRatingComponent 0x50CFE0     (weight 0xE521B4)
s = clamp01( s + 0.239 * starPower )                       // virtual 0x94, CStudio_GetStarPowerRatingComponent 0x50FC90 (weight 0xE521B8)
s = clamp01( s + 0.144 * awards )                          // virtual 0x98, CStudio_GetAwardsRatingComponent 0x50D8E0    (weight 0xE521BC)
studio.rating = s
```
The weights read from the exe are the three at `0xE521B4..BC` (0.239, 0.239, 0.144); a least-squares fit of the five weights to the 27 rows gave 0.1447 / 0.2386 / 0.2388 / 0.2389 / 0.1434, so appearance is 0.144 and reputation 0.239 (their constants, just below `0xE521B4`, have not been read). An earlier version of this section had 0.15 / 0.30 / 0.30 / 0.30 / 0.15, which was wrong. The five weights add to 1.005, so a perfect studio is capped at 1. Implemented as `web/src/sim/studio/StudioRating.ts` (`web/tests/sim/studioAndAi.test.ts` holds logged rows).
- **Decayed reputation** = stored reputation (+0x138) * exp(-(ln 2 / 5) * years since it was stored (+0x13C)), **[verified, 27 rows within 1e-4]**: it halves every 5 years (constant 0xE52188 = 0.138629). The earlier text said `exp(-0.01 * years)`, which is wrong. The player's studio starts with stored reputation 0.1717 stored in 1957.76 (so 0.1244 at the start of 1960).
- **Money component**: studio money (virtual 0x24) compared with a six-entry int64 threshold table at 0x104BD38: starts at -0.2, +0.2 for each threshold passed, linear interpolation inside the current bracket (money scale 2^-23), clamped; below the first threshold the result is 0. Not yet checked against the log (AI studios sit at 1.0, the player's at 0.91).
- **Star power**: take the ratings of the studio's stars (list at +0x94, `TMCharacter_GetStarRating`), repeatedly pick the highest, add `rating * w` with w starting at a constant (`0xE521C0`, 0.4 in the old text) and falling by `0xE521C4` (0.05) per star, clamped after each addition. Not yet checked: the log has the value (0.22-0.49 for AI studios) but not the stars' ratings.
- **Awards**: number of award entries whose owner (+0xB8) is this studio times 0.1695 (about 1/5.9), clamped (0, 0.1695, 0.339, ... in the log).
- Consequence: appearance and awards are the smallest terms (0.144 each); reputation, money and star power carry 0.239 each.

**Where the studio rating is read** (call sites that fetch the player studio then call virtual 0x84): 0x574AA0 scales it by a 16-bit constant at 0xE531FC (= 5) and rounds (likely the number of arrivals of some NPC type per period, minimum 1 during a tutorial), 0x84E610 blends it with a field at +0x120 for a similar count, 0x8633C4/0x8634C5 (UI), and 0x8F38A0 (a getter object, probably an objective/advice value). These functions are not defined in Ghidra yet, so their exact purpose is unconfirmed.

## 3ax. CLot (save variables, lot-wide metrics) and CShoot crew validation
**CLot** (`Lot.cpp`; `CLot_RegisterSaveVariables` 0x4667E0 then `CAsset_RegisterSaveVariables`): `(int&)CurrentSize` (+0x408), `SL_CamPos` (+0x428, 12 bytes), `SL_CamFoc` (+0x434, 12), `SL_CamZoo` (+0x440), `SL_CamRot` (+0x444), `SL_GameSpeed` (+0x448), `SL_Version` (+0x44C, string). `CLot_PreSave` (0x467910) fills the camera and version fields from the live camera and game. Lot-wide metrics used by the studio appearance of 3av/3aw:
- `Lot_GetCleanliness` (0x466290) = clamp01( 1 - litter / 30 ), litter in the global at 0xF8904C.
- Lot virtual 0xB8 (0x467E80, not a Ghidra function) = mean of virtual 0xB8 (state of repair) over all assets for which virtual 0x10C is true, i.e. the average condition of the lot (this is the `1 - lot condition` penalty term of `CStudioPlayer_UpdateAppearance`).
- Lot virtual 0x188 (0x466310) = clamp01(lot +0x45C). That field is the lot's **layout score**: a routine at about 0x4695A0 (not a Ghidra function) computes a per-asset value in asset +0x19C from a pairwise relation (asset virtual 0x178 between each asset and the others, normalised by the asset count) and stores the mean over all assets in lot +0x45C. Its inputs and meaning (adjacency, aisle clearance?) are not decoded; it contributes `0.25 * clamp01(layout score)` to the appearance.
- `Lot_GetMinAssetMetric` (0x468030) = minimum of asset virtual 0xF0 over all assets, clamped 0..1.

**CShoot** (a scheduled shoot slot; `CShoot_*`): rooms/slots are four vectors of 0x18-byte entries at +0xA8 (role 7 cameraman), +0xB8 (role 8 soundman), +0xC8 (role 10 dolly operator) and +0xD8 (role 12 clapper man) using the staff job numbers of 3ad; the assigned CStaff is stored at entry +0x14. `CShoot_SetShootController` (0x4DC8F0, +0x10C) resizes the four vectors to the shoot controller's slot counts; `CShoot_SetSlotAssignee` (0x4DC880) sets one entry.

`CShoot_ValidateCrewAndCast` (0x4DCB40) checks the shoot and records problems with `ShootProblems_Add` (0x4DC690) into the structure at +0x12C. Problem codes: byte flags 1 (no cameraman found/available), 2 (no soundman), 3 (dolly operator), 4 (clapper man), 5 (cast member/ director cannot be placed), lists for 10 (staff member cannot fill the slot), 11 (star belongs to another studio), 12 (not used here), 13 (star/actor unavailable: virtual 0x1DC true), 14 (costume change needed; `TMCharacter_SetBaseCostume` is applied for cast that pass). The function returns true only if no problem was recorded, and auto-assigns missing crew with `FUN_005B6EE0` (a "find free staff of this role" helper). `CShoot_IsReadyToShoot` (0x4D7060) additionally requires a director, that every cast entry is usable, that the shoot controller's set is ready (virtual 0x164) and that the controller state is 4 (finished) or the project's active controller is ready.
