# Libraries and shared engine code inside `MoviesSE.exe`

A large part of the binary is not *The Movies* at all: it is third-party libraries and Lionhead middleware shared with *Fable*. Knowing where that code is
matters for two reasons: it can be named from upstream sources instead of read function by function, and **the reimplementation does not port it** (the web
app uses fflate for zlib and the browser's own audio decoding). This page says what was found and how.

The data files: `library_map.csv` (every function in the shared window, regenerated by `tools/library_map.py`), `fable_matches.csv` (Fable hints,
`tools/match_fable.py`), `renames.csv` (verified names with their evidence), and for the networking code `net_map.csv` / `p4api_map.csv` (`NETWORK.md`).

## What is in the binary

| Library | Where | Notes |
|---|---|---|
| zlib 1.1.4 | `0x00b2....`-`0x00bb....` | the game's own copy; 35 functions named, deflate half included; the `_tr_*` functions of `trees.c` are not named |
| zlib 1.0.4 | `0x00a3....`-`0x00ac....` (`*_copy2`) | bundled with the statically linked Perforce P4API client (`NETWORK.md`); 29 functions named |
| libogg (1.1 era) | in the shared window | 40 functions: `framing.c` and `bitwise.c` |
| libvorbis 1.0.1 (`Xiph.Org libVorbis I 20030909`) | in the shared window | 69 functions: `info.c`, `sharedbook.c`, `codebook.c`, `smallft.c`, `mdct.c`. No floor, residue, mapping, window or psychoacoustic code was found, so those parts appear not to be linked (not exhaustively ruled out) |
| Perforce P4API | see `NETWORK.md` | 306 functions mapped |
| Lionhead middleware | `0x00bc0000`-`0x00c9a000` | shared with Fable: OpenAL wrapper, DSP and codec stack, `PK*` threads, containers and disk readers, `LLA`/`LHA` audio, CPU detection, hashing. About 40% named |
| MSVC 7.1 CRT/STL | throughout | 622 functions identified by Ghidra's FID |

## How the shared window was matched against Fable

*Fable: The Lost Chapters* (Lionhead, 2004-05, MSVC 7.1) shares a library window with *The Movies* (`BuffJesus/FableDecomp`). In our binary it is
`0x00bc0000`-`0x00c9a000`; in Fable around `0x00c00000`-`0x00cb0000`. Signals, each checked by hand:

1. Every quoted string in our export against every string in both projects (source, symbols, Ghidra dumps, docs).
2. Normalised pseudo-C similarity (4-gram shingles with variable and address names removed) against about 9,300 function bodies in Fable's dumps.
3. Function sizes: in the matched region 446 of 511 functions have exactly the same size, so it is the same source built the same way. Runs of six or more
   consecutive identical sizes give matches even where Fable has no decompiled body.
4. Class names, RTTI names and numeric constants against both projects' symbol lists.

Result: 1,154 of the 4,852 functions in the window matched (186 on body similarity alone; 368 on a size run with similarity 0.6 or more; 117 on a size run with
lower similarity; 483 on a size run only; 142 rows at 0.95 or more).

**Fable's names are hints, not names.** None of the matched functions carry names Fable's project derived from debug symbols; they all come from its automatic
naming, which describes behaviour and is sometimes wrong (a 4,202-token audio convolution is called `Graphics_RenderTextWithConditionalEffects`, the Ogg page
checksum `CRC32_ComputeBuffer`, four x87 `10^x` routines `Pow2_Float`). Only names checked against our own code go into `renames.csv`.

**Black & White** (`openblack/bw1-decomp`) shares almost nothing: the `LHFile` segment container (`AUDIO.md`; our `CLHSegmentReader` is a rewrite of the same
format under a new class name, the write side matches too), 34 trivial strings, upstream zlib 1.1.3. Its `LHParseFile`, `LH3DMath`, `LHLog`, `LH3DMesh` and the rest
have no counterpart: B&W was built with MSVC 6 and an older library generation.

**The HTTP client** (`"Lionhead Studios TheMovies Client (HTTPLib) 1.0"`) does the same job as Fable's `LHHttp2` but is a different implementation (body similarity
0.2 to 0.36). It is described in `NETWORK.md`.

## How the rest of the window was named, most reliable first

1. **Source-file assertions.** The library logs `.\File.cpp(line) : message`, which names the class and often the method (`PKCSemaphore`, `PKDiskBufferingCReader`,
   `PKContainersCRedBlackTree`, `PKDataReadCWindow`, `PKStringsCHeapString`, `PKAllocatorsCPooledMemory`, `LLACodaCChannel`, `CFrame`, `CInstance`, `CASyncDecoder`,
   `OggVorbisLibWrapper`, `MapAnalysisImp*`, `RiffCInfo`, `CSFXTimeline`, ...): about 110 read and named `Class_Method`. Header assertions from the `libpk` headers
   (`PKCAutoDelete.h`, `PKCArray.h`, `PKAllocatorsLinkTime.h`, `PKCMailbox.h`, ...) name 84 template instantiations by header line.
2. **The red-black tree** `PKContainersCRedBlackTree`, complete. Nodes are `{left, right, parent, ..., object at +0x10}`; used by the segment reader, the disk
   reader and the map-analysis classes.
3. **Win32 and OpenAL wrappers**: 44 single-call wrappers named by the API they call (`Wrap_CloseHandle_...`), 33 lazy OpenAL loaders by the function they resolve.
4. **Compiler-generated patterns**: 388 scalar deleting destructors, 289 destructors called only from those, 314 constructors and 92 vtable setters. Functions sharing a
   vtable address belong to one class (`Ctor_vt00d9fb18_...`).
5. **Templates**: `LH_Array_*` and the MSVC 7.1 sort internals (`LH_Sort_Med3`, `PushHeap`, `AdjustHeap`, `UnguardedPartition`, `InsertionSort`): 75 functions.
6. **Small helpers** whose body is a few lines (`Util_PopCount`, `Util_CeilLog2`, `Math_Vector3Length`, `Jenkins_Hash_Lookup2`, `CPU_InitCapabilities`, ...).

zlib was identified by its message strings, `stream_size == 0x38`, adler32's 65521 and 5552, the deflate states 42/113/666 and the version check strings
(`"1.1.4"`, `"1.0.4"`). libogg and libvorbis were named by reading the code next to the upstream sources (`xiph/ogg` `v1.1.1`, `xiph/vorbis` `v1.0.1`); function order
follows the source files.

**A file list of Fable's source tree** (`TalonBraveInfo/fable-source-tree`) helped with class names. It is not source code: every Lionhead file in it is a
56-byte stub generated from the paths in a 2004 Fable build's debug symbols. It gives the class names of the audio library in an earlier branch (`ver06_fable6`;
ours is `ver06_movies2`): the same `CCodaFrameStreamer`, `CFrame`, `CASyncDecoder`, `PKCSemaphore`, `PKCThreadManager`, `PKSerialiseCParser`...; renamed ones
(`CFileSegmentReader` = our `CLHSegmentReader`, `CTimeline` = `CSFXTimeline`); and the game audio engine classes (`CDistanceModel`, `CDriver`, `CBank`, `CEventTriggers`,
`CAtmosSystem`, `CMixer`, `CVirtualPlayer`...). Class names only, so they pick the prefix for an unnamed function, not its name.

## What is left

- 2,987 functions in the window are still `FUN_*` (551 of them 200 bytes or larger); 820 have a Fable hint not adopted. The largest unnamed blocks are after
  `MapAnalysisImpCGroupModel` (about 400), between `PKCTimerManager` and `PKDiskBufferingCReader` (about 380), and between `PKAllocatorsCPooledMemory` and
  `CVSTParameters` (about 250).
- The game's own audio engine (`0x00bf3000`-`0x00c02000`, `0x00bc0000`-`0x00bc9000`) is Movies-specific and needs reading function by function (`AUDIO.md`).
