# Networking code in MoviesSE.exe

The online services are long gone, so this is a map of what to stub or ignore, not a plan to revive anything.
Generated by `tools/net_map.py` into `net_map.csv` (one row per function: stack, layer, evidence, class). Regenerate, do not edit.

## Method

* **Bottom-up.** Seeds are functions that call Winsock / wininet / iphlpapi, or carry HTTP / protocol strings. The set of direct
  calls around them, inside the address windows below, is the net library. Direct calls only: virtual dispatch is invisible.
* **Top-down.** Functions of the online UI classes (`WOnline*`, `WLeague*`, `COnlineLeagueTableEntry`) and anything that mentions an
  `ONLINE_*` key, `CDKey`, `UserAccountName` or the proxy settings, tagged by feature and marked `reaches_net` when a chain of at most
  four direct calls gets into the library.
* **Gotcha.** Stack A imports WS2_32 *by ordinal*, so the decompiler shows `Ordinal_18(...)` rather than `select(...)`. The tool maps
  the ordinals (1 accept, 3 closesocket, 4 connect, 9 htons, 10 ioctlsocket, 16 recv, 18 select, 19 send, 23 socket, 52 gethostbyname,
  111 WSAGetLastError, 115 WSAStartup, ...). A name-only search finds only stack B and misses the real client.

**Stack B** (`0x00a9f9d0`, `0x00abc330`, `0x00ac61b0`-`0x00ac6f90`, 19 fns) is a plain TCP wrapper imported by name
(`WSAStartup`, `gethostbyname`, `getservbyname`, `send`, `recv`, ...), whose only callers are in `0x00a87700`-`0x00aa05d0`.
The strings there (`client`, `server2`, `xfiles`, `language`, `unicode`) and the RTTI (`Perforce::CClientUser`, `MyAsyncInteraction`,
`LSocketConnError`) say this is the Perforce P4API client, i.e. leftover source-control tooling, nothing to do with the online
services. `class_attribution.csv` labels two of its functions `zlib`; that attribution is wrong.

Stack A's transport is a general socket class (it can `bind`/`listen`/`accept`, not only `connect`); whether anything uses the
server side has not been checked.

## Does a normal session touch it?

`coverage_sets.json` (boot, main menu, new-game load): **no** transport, HTTP or protocol function is reached. The 10 UI functions
reached are `WOnlineOptions` (9) and `WLeagueScreen` (1), which is the options page being built, and one glue function. So the
library only runs when the Online screen is opened. `steady_gameplay` is empty in that file, so this has not been checked for a
played month.

## Caveats and open items

* Virtual calls are not in the call graph. UI methods reached only through vtables are tagged by class (`ui_only`), so "ui_only"
  means "no direct-call path found", not "provably offline".
* The `glue` set is every function of the window that connects to a seed by direct calls (distance 1-6). It is probably the library's
  private helpers, but a few could be shared; `shared` marks the ones with callers outside the cone or STL-style helpers.
* Other callers of the library that are not UI classes and are still unidentified: `0x009c2540`, `0x009c25f0`, `0x009c26a0`,
  `0x009c2df0`, `0x009c3010`, `0x009c5090` (they call into `0x00963fa0`/`0x00964450`/`0x0096a0f0`; not yet looked at, possibly
  shared helpers rather than net users), `0x00a88da0`.
* `ShellExecuteA` callers (`0x00a0f240`, `0x00ab4df0`) open URLs or files externally; they are not in the cone.
* Protocol details (what `Rav0`, the `%d%d%s%s` signature at `0x00965680` and the MV error codes mean) are not decoded.
