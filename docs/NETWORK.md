# Networking code in MoviesSE.exe

The online services are long gone, so this is a map of what to stub or ignore, not a plan to revive anything.
Generated by `tools/net_map.py` into `net_map.csv` (one row per function: stack, layer, evidence, class). Regenerate, do not edit.
`tools/net_map.py` and `tools/p4api_map.py` read the decompile export (`data/ExportDecompiled`), `tools/ghidra_names.csv`,
`renames.csv` and, for the class column, `docs/generated/class_attribution.csv` (all local or generated; run
`python3 tools/callgraph.py --build` first whenever the names change, because the call graph is cached).

## Method

* **Bottom-up.** Seeds are functions that call Winsock / wininet / iphlpapi, or carry HTTP / protocol strings. The set of direct
  calls around them, inside the address windows below, is the net library. Direct calls only: virtual dispatch is invisible.
* **Top-down.** Functions of the online UI classes (`WOnline*`, `WLeague*`, `COnlineLeagueTableEntry`) and anything that mentions an
  `ONLINE_*` key, `CDKey`, `UserAccountName` or the proxy settings, tagged by feature and marked `reaches_net` when a chain of at most
  four direct calls gets into the library.
* **Gotcha.** Stack A imports WS2_32 *by ordinal*, so the decompiler shows `Ordinal_18(...)` rather than `select(...)`. The tool maps
  the ordinals (1 accept, 3 closesocket, 4 connect, 9 htons, 10 ioctlsocket, 16 recv, 18 select, 19 send, 23 socket, 52 gethostbyname,
  111 WSAGetLastError, 115 WSAStartup, ...). A name-only search finds only stack B and misses the real client.

**Stack B** (`0x00a9f9d0`, `0x00abc330`, `0x00ac61b0`-`0x00ac6f90`, 19 fns; see "P4API" below) is a plain TCP wrapper imported by name
(`WSAStartup`, `gethostbyname`, `getservbyname`, `send`, `recv`, ...), whose only callers are in `0x00a87700`-`0x00aa05d0`.
The strings there (`client`, `server2`, `xfiles`, `language`, `unicode`) and the RTTI (`Perforce::CClientUser`, `MyAsyncInteraction`,
`LSocketConnError`) say this is the Perforce P4API client, i.e. leftover source-control tooling, nothing to do with the online
services. `class_attribution.csv` labels two of its functions `zlib`; that attribution is wrong.

Stack A's transport is a general socket class (it can `bind`/`listen`/`accept`, not only `connect`), but the server side looks
dead: `listen` (`0x0096b250`) and `accept` (`0x0096b430`) are reached only through `0x0096f9f0` / `0x00970e50`, whose only
callers are `0x00970bb0` and `0x00971190`, and those have no direct callers and no vtable or data references.

## The socket and HTTP classes, as named

34 functions are named in `renames.csv` (evidence in each row), applied to the Ghidra project and `tools/ghidra_names.csv`.
The picture they give:

* **`NetSocket`** (`0xc4` bytes, one `operator_new(0xc4)` per socket). Fields seen: socket handle `+0x58` (-1 = closed), peer
  `sockaddr` `+0x5c`, type `+0x80` (1 stream, 2 datagram, 3 something else that `Receive` refuses), send buffer `+0x88..+0x8c`,
  bytes sent `+0xb0`. The constructor runs `WSAStartup(2.2)` once and links every socket into a global list (`DAT_01050b28`).
  Methods: `Constructor` `0x96be00`, `Destructor` `0x96c8f0`, `Close` `0x96bf10`, `SetNonBlocking` `0x96b0f0`,
  `OpenBound` `0x96b920`, `ConnectAsync` `0x96ba70`, `ConnectBlocking` `0x96bb40`, `PollConnect` `0x969cf0`, `Send` `0x969d90`,
  `FlushSendBuffer` `0x96aa40`, `Receive` `0x96c410`, `WaitReadable` `0x969ba0`, `WaitWritable` `0x969c50`,
  `QueryBytesAvailable` `0x969de0`, and the server-side `Listen` / `Accept` / `CreateListener` (dead, see above).
  Every Winsock failure is turned into a `"Winsock Error: <code>"` string.
* **`NetAddress`** helpers: `ResolveHost` (`inet_addr`, then `gethostbyname`), `ResolveCached` (result cached at `+0x1c`),
  `FromSockAddr`, `ToSockAddr`.
* **HTTP client** (`LHHttp_*`): `BuildRequest` `0x96e860` (GET/POST), `PumpSend` `0x96e270` (a small state machine: state 2 waits for
  the connect, then sends the request in chunks of up to 4 KiB, then state 1), `SendBytes` `0x96d1d0`, `ReceiveResponseHeaders`
  `0x96ed70`, plus the three that were already named. The connection object holds its `NetSocket` pointer at `+0`.
* **MV replies**: `MV_ParseMVX301Reply`, `MV_ParseMV0050Reply` (header plus a list of 0x50-byte records, used by the Online screen at
  `0x6d3fe0`), `MV_ParseMV0040Reply` (embedded blobs written to `sy*.tmp` temp files, used at `0x6c73c0`). The numbers are the
  reply's type tag, not yet matched to features.
* **Proxy autodetect**: `Net_AutoDetectProxy` `0x969740` (probe request, then port 8080, then `Net_QueryWininetProxy` through
  `InternetQueryOptionA`), called by `WOnlineAutoConfig_Tick`. `Net_QueryAdaptersInfo` (`GetAdaptersInfo`) has no callers.

Names were checked by reading the decompiled bodies, not by running anything; two were corrected while writing (`LHHttp_PumpSend` was
first taken for a body receiver). Treat the field offsets as the decompiler's view.

## Does a normal session touch it?

`coverage_sets.json` (boot, main menu, new-game load): **no** transport, HTTP or protocol function is reached. The 10 UI functions
reached are `WOnlineOptions` (9) and `WLeagueScreen` (1), which is the options page being built, and one glue function. So the
library only runs when the Online screen is opened. `steady_gameplay` is empty in that file, so this has not been checked for a
played month.

## Caveats and open items

* Virtual calls are not in the call graph. UI methods reached only through vtables are tagged by class (`ui_only`), so "ui_only"
  means "no direct-call path found", not "provably offline".
* `glue` = connected to a seed by direct calls without passing through a `shared` function; `shared` = also called by something
  that is neither net nor UI (or flows down from such a function); `loose` = only connected through shared functions. All three
  are heuristics. The "unidentified callers" in `0x009c2xxx` and `0x00a87700`-`0x00a8e330` / `0x00a88da0` turned out to be
  MSVC STL (`std::string`, vector/list helpers), i.e. users of the shared helpers, not users of the net library.
* `ShellExecuteA` callers (`0x00a0f240`, `0x00ab4df0`) open URLs or files externally; they are not in the cone.
* Protocol details (what `Rav0`, the `%d%d%s%s` signature at `0x00965680` and the MV error codes mean) are not decoded.

## P4API (stack B and what surrounds it)

`tools/p4api_map.py` writes `p4api_map.csv` (306 functions): the statically linked Perforce client, not part of the game's
online services. Its objects sit between `0x00a9d470` and `0x00ac7ee0`, interleaved with unrelated game code (the pak writer at
`0x00aafeb0`-`0x00ab4df0`, FX, fonts), so membership is "connected to the P4 anchors by direct calls, minus functions carrying game
strings". Anchors: `P4PORT`/`P4HOST`/`P4USER`/`P4CONFIG`..., `Rpc_dispatch`, `NetBuffer_send_compressing`,
`NetTcpTransport_*`, AppleSingle, charset tables (`shiftjis`, `macosroman`).

| sub | functions | what |
|---|---|---|
| net | 27 | `NetTcpTransport`, `NetBuffer`, Rpc, the Winsock calls of stack B |
| config | 10 | `P4*` environment variables, registry, `COMPUTERNAME`/`USERNAME` |
| file | 17 | file-system layer (`open_for_read`, handles, AppleSingle, permissions) |
| charset | 1 | `shiftjis`, `winansi`, `macosroman` tables |
| zlib-1.0.4 | 34 | the **second zlib copy** (`*_copy2` plus unnamed functions that only touch it), bundled for `NetBuffer` compression |
| interleaved | 30 | unnamed functions lying between P4 members at `0xac2240`-`0xac7c90` with no call link to anything (virtual methods); same object files, so P4, but **no call evidence** |
| other | 187 | the rest of the client, mostly unnamed |

The second zlib copy is `"1.0.4"` (the first, used by the game, is 1.1.4) and is called from `NetBuffer`'s compress/decompress
code, so it belongs to P4API as well. 48 functions of the client had been attributed to `zlib` by adjacency in `class_attribution.csv`.
`tools/attribute_classes.py` re-labels every map member except the zlib ones `P4API` (tier `lib`) when `p4api_map.csv` is present.
This was run against the real exe (the output is gitignored): 272 functions are now `P4API`, and the only functions in
`0xa90000`-`0xad2000` still labelled `zlib` outside the map are `0x00ac1480` and `0x00ac14e0` (unresolved: not call-linked to
either P4 or zlib). A first version of the map missed `0x00ac65b0` (the `gethostbyname` wrapper, no P4 string) and `0x00ac8050`
(zlib); the Winsock-caller anchor and the zlib neighbour rule fixed that.

Side effect of the network names: the attribution tool turns a name prefix into a class, so `MV_ParseMV*` made it label about 51
neighbouring functions (`0x00965c80`...) with a class called `MV`, which is also the engine's real namespace (`MV::Object`...).
Read that label as "net protocol code", or rename the three functions if it gets in the way.

The game's own glue on top is `Perforce::MyFileSys`, `Perforce::ClientUserSubclass` and `MyAsyncInteraction` (RTTI, around
`0x00971790`-`0x00974820`); nothing in the cone calls it, and it has not been looked at.
